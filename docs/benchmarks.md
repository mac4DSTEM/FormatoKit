Reading it: "Python / kit" above 1 is the kit faster. The Velox SI row is the stream decode (RosettaSciIO: numba-jitted, warm). The MIB and MRC rows are byte-swap and copy at memory speed; MIB reads were 934 ms at the first measurement (see below).

## Backend decision per function (D16)

Readers stay on the CPU: they are bound by file reads and memory copies, there is no arithmetic for a GPU to take over, and
host-to-device copies of a freshly read array cost more than the read. Measured break-even: none exists, no Metal path is a work item
for any reader. Threading and mmap: only the 4D loads above 100 MB could split a read over cores; at the typical size the 4D rows
are already within 1.1x of h5py and of RosettaSciIO, so the question belongs to the nightly large rows (open-items).

| Function | Backend | Why |
|---|---|---|
| DM, TIFF, MRC, MIB, EMPAD, HDF5 4D, Velox images and spectra, MSA | CPU only | read-bound; no per-element arithmetic beyond byte swaps |
| Velox spectrum-image decode | CPU only | sequential stream with data-dependent branches (markers); the kit is already 3.3x RosettaSciIO's numba loop at 128² |

## Slower than RosettaSciIO at the typical size

Listed first in `docs/open-items.md` with the cause. Found and fixed in this session (diagnosed with `sample`, then measured):
MIB 934 ms to 35 ms (an `ISO8601DateFormatter` built per frame header, 1024 times, plus a per-pixel `Data.append`); MSA 111 ms to 17 ms
(per-line allocation in the first reader).
